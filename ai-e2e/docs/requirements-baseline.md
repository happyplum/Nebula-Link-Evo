# AI E2E 产品需求基线

> 状态：已确认目标需求，尚未全部实现。
> 更新时间：2026-08-12。
> 本文记录产品边界与验收语义，不规定数据库表、接口字段、脚本 DSL 语法或实施顺序。当前实现状态以代码和 `ai-e2e/PRODUCT-SPEC.md` 为准。

## 1. 产品定位

`ai-e2e` 是基于 PRD 与已完成网页的 E2E 测试业务层。它负责把需求理解、页面探索、测试资产生成、场景编排、可视执行、结果验证和局部修复组织成可维护闭环。

系统分为三层：

- `proxy-adapter`：浏览器与 Playwright/CDP 能力的唯一所有者，通过 MCP 提供页面分析、操作、实时画面和执行证据。
- `ai-chat-service`：AI 基础能力层，提供分析/决策模型、单次视觉分析、MCP 工具编排和未来 Skills runtime。
- `ai-e2e`：E2E 业务层，持有 PRD、业务版本、页面、功能模块、功能脚本、测试场景、任务依赖、运行上下文和结果报告。

首次提供 PRD 与目标链接时，系统从零分析并生成测试资产；后续运行优先加载已有资产，由子代理验证并在职责范围内修正。

## 2. 领域层级

```text
业务版本
├─ PRD 原文、解析结果与决策文档
├─ 页面（URL + 路由/查询参数锚点）
│  └─ 功能模块
│     └─ 多个功能脚本
└─ 测试场景
   └─ 编排多个功能脚本调用
      ├─ 顺序与依赖
      ├─ 重复调用
      ├─ 输入输出绑定
      └─ 预期结果
```

### 2.1 页面

- 页面由规范化 URL（包含 path/hash route）与路由/查询参数共同锚定。
- 一个页面可以包含多个有顺序的功能模块。
- DOM 基线、元素定位信息和参考截图属于页面的版本资产，但每次执行仍必须重新检查当前页面状态。

### 2.2 功能模块与功能脚本

- 功能模块是页面内的业务功能分组，例如“用户维护”。
- 一个功能模块可以拥有多个功能脚本，例如新增用户、编辑用户、单个删除和批量删除。
- 功能脚本是最小的复用、独立执行、验证、修复和重复调用单元。
- 功能脚本可以操作当前页面内的弹窗、抽屉或页面跳转，但不得继续承担另一个页面模块的业务职责。
- 跨页面业务由测试场景组合不同页面的功能脚本完成。

### 2.3 测试场景与 PRD 流程

- 测试场景是完整业务目标和验收单位，可以包含多个功能模块、多个功能脚本和多个页面。
- PRD 负责形成测试流程与 TODO，定义脚本调用顺序、依赖、重复次数、参数传递和预期结果。
- 同一功能脚本可以在场景内重复调用。例如批量删除前可以多次调用新增用户脚本。
- 一个脚本的输出可以成为后续脚本的输入。例如新增用户输出用户标识，删除用户消费该标识。
- 脚本只完成自身业务操作，不在内部擅自编排登录、造数或其他场景外脚本。

## 3. 业务版本与复制

- 业务版本由用户显式创建。
- 版本记录来源版本，并可记录部署标识和 Git 标识。
- `copy` 产生完全独立、可修改的资产快照，后续生成和修复不得覆盖来源版本。
- 复制范围包括 PRD、解析结果、决策文档、页面锚点、功能模块、功能脚本、测试场景、TODO、变量定义、DOM 基线、元素定位信息和参考截图。
- 新版本内的资产拥有独立身份和引用关系；来源版本只用于追溯，不形成可变共享引用。
- 运行历史、失败证据、临时运行变量、实际测试数据、登录状态、Cookie、Token 和其他密钥不随版本复制。
- 被复制的 DOM、定位和截图只是新版本的初始参考；每次运行仍执行重新检查。

## 4. 代理职责

### 4.1 主代理

主代理负责：

- 理解完整 PRD，生成或维护测试流程、TODO 和依赖关系。
- 维护全局运行上下文及功能脚本之间的数据传递。
- 按页面和场景职责拆分任务，向子代理派发明确的输入、脚本调用、预期结果和允许写回的输出。
- 接收子代理结果，决定继续、暂停、插入前置任务、恢复、跳过或结束流程。
- 处理登录、测试数据准备等跨场景前置条件；子代理不得自行补做。
- 对需要裁决的问题作出决策；会影响需求、验收或后续维护的决定必须先写入当前业务版本的决策文档，再恢复执行。
- 汇总通过、失败、中断、暂停和跳过结果及其证据。

主代理可以调用视觉模型完成一次明确的页面分析，但视觉模型不接管调度。

### 4.2 子代理

- 子代理负责主代理派发的页面场景片段，只执行任务中明确授权的功能模块和功能脚本。
- 子代理执行脚本、重新检查页面、验证结果，并在职责范围内修正失效脚本，最后结构化汇报结果、输出数据和证据。
- 子代理不得擅自登录、创建缺失数据、调用场景外脚本、改变业务断言或扩大任务范围。
- 子代理发现意外登出、缺少外部前置条件或进入错误页面时，当前执行尝试失败并上报，由主代理安排后续动作。
- 子代理认为需要主代理裁决时，应暂停操作、保存现场和恢复检查点，并提交问题、影响和候选方案。
- 大多数派发创建干净的新代理上下文。对于登出等可恢复的意外中断，主代理可以恢复原子代理上下文；如果上下文已失效，则创建干净上下文并加载原任务、检查点和获授权变量。
- 代理记忆不是长期资产；可复用结论必须写回版本文档、页面资产或功能脚本。

### 4.3 视觉模型

- 主代理和子代理都可以调用视觉模型。
- 每次视觉调用只处理一个边界明确的分析任务，例如识别页面状态、解释截图与 DOM、查找目标元素或比较变化。
- 调用方必须为每次调用提供完整输入。
- 视觉模型不保存流程状态、不连续执行任务、不调度脚本、不操作浏览器，也不决定下一项业务任务。
- 视觉输出必须是可序列化证据，不得跨服务返回 `Page`、`Locator` 或 `ElementHandle` 等进程内 Playwright 对象。

## 5. 功能脚本与执行方式

### 5.1 权威脚本资产

- 系统内的权威资产是结构化、参数化的语义功能脚本，不是要求用户阅读的传统 Playwright `.spec.ts` 文件。
- 功能脚本应能表达业务步骤、浏览器动作、目标语义与定位依据、变量引用、前置检查、操作后验证、预期输出和恢复检查点。
- 场景通过受控的编排结构调用脚本，而不是把完整测试流程硬编码进单个脚本。
- 直接导出并运行 `npx playwright test` 不是当前验收目标；未来可以作为派生产物，不得取代系统内的权威语义脚本。

脚本 DSL 的精确字段、允许的控制结构和校验规则尚待技术设计，不在本文中提前锁定。

### 5.2 唯一浏览器执行链

- `proxy-adapter` 是功能脚本和探索动作的唯一浏览器执行入口。
- `ai-e2e` 不应为目标运行链启动独立 Playwright/Chromium 进程；主代理、子代理和修复验证不得使用不可观察的浏览器操作旁路。
- 语义指令通过 `ai-chat-service` 的 Agent/MCP 能力发送给 `proxy-adapter`，由其映射为 Playwright 操作。
- 所有浏览器操作都必须在实时画面中可见，并能关联到当前场景、功能脚本和步骤。
- 目标体验是让人通过实时画面、操作说明和结果状态理解测试过程，而不必阅读底层脚本。
- 操作记录必须支持复现；后续可在 `proxy-adapter` 的指令执行画面上增加高亮、鼠标移动、点击、输入、滚动和断言等操作动画。

### 5.3 固定重新检查

每次执行都包含重新检查，而不是只在版本复制或脚本修复后检查一次：

1. 获取当前页面状态及最新 DOM/截图证据。
2. 检查页面身份、路由、登录状态和场景前置条件。
3. 每个操作前重新解析并确认目标元素。
4. 操作后验证页面变化和业务结果。
5. 恢复中断任务前检查中断前操作是否已产生副作用。

恢复单位是经过状态确认的语义步骤，不是脚本代码行。状态不确定时不得盲目重复可能产生副作用的操作。

## 6. 运行上下文、失败与恢复

### 6.1 运行上下文

- 全局运行上下文按一次测试流程隔离，由主代理维护。
- 子代理只读取任务授权的输入，并只写回任务声明的输出。
- 运行变量可以贯通不同功能脚本，例如把新增用户的输出交给后续删除脚本。
- 运行变量和实际测试数据不写入业务版本，也不泄漏到其他测试流程。

### 6.2 失败、中断、暂停与跳过

- 业务执行失败必须记录，不得通过放宽断言或静默跳过伪造成通过。
- 子代理上报失败时必须说明是否阻碍后续场景、已产生哪些部分数据或页面副作用，以及缺失哪些预期输出。
- 主代理依据 TODO 依赖关系决定影响范围。依赖失败输出的后续任务可以跳过；不受影响的任务可以继续。
- 意外登出属于可恢复中断：子代理停止当前任务并上报，主代理安排登录任务，再依据检查点和副作用检查决定恢复或重派。
- 需要主代理作出业务或验收决策时属于暂停，不等同于测试失败。决策持久化到当前业务版本后才能恢复相关任务。
- 被跳过的任务必须保留原因和上游依赖，不能计为通过。

状态名称、持久化字段和完整转换表在技术设计阶段确定；实现必须能够区分运行、通过、失败、可恢复中断、等待决策、依赖跳过、取消和完成。

## 7. 失败证据

任何失败都必须在上报主代理前固化现场，至少包含：

- 失败时截图；能够确定目标位置时同时保存标注证据。
- 当前 URL、页面标题与 DOM 快照。
- 业务版本、测试流程、场景、功能脚本、脚本调用和失败步骤的关联信息。
- 期望结果、实际结果、已执行步骤和错误说明。
- 脱敏后的输入、输出、部分数据与可能副作用。
- 是否阻碍后续任务及建议的恢复条件。
- 时间信息和可用于关联操作记录的运行标识。

失败证据归属于具体运行，不写回版本基线。只有修复经过重新执行和验证后，新的 DOM 基线、定位信息或功能脚本修订才写入当前业务版本。

证据格式、保存期限、脱敏规则和是否引入 trace/video 尚待技术设计。

## 8. 脚本修复边界

- 子代理可以在当前页面场景片段内修复 DOM、定位器和交互方式变化造成的功能脚本失效，并重新验证。
- 修复只写入当前业务版本，不覆盖来源版本。
- 需要调用其他场景、补充登录或准备外部测试数据时，必须上报主代理调度。
- 修复如果会改变 PRD 含义、业务预期、断言口径、数据安全边界或其他场景契约，必须暂停并由主代理决策；需要用户决定时由主代理继续上报。

## 9. 当前实现差距

以下是经代码核对确认的现状，不得描述为已交付目标能力：

- 当前数据链是项目 → 业务模块 → 功能模块 → 测试场景 → TypeScript 脚本版本，没有业务版本、显式页面实体、功能脚本实体、场景调用图或版本复制模型。
- 当前脚本归属于单个测试场景，不能表达“一个模块包含多个功能脚本，再由跨模块场景编排”。
- 当前 `ExecutorService` 把 TypeScript 写入临时文件并用 `npx tsx` 子进程执行；这与目标唯一可视浏览器执行链冲突，后续必须替换而不是继续扩展为目标执行器。
- 当前运行记录主要关联单个脚本，只支持 pass/fail/error/timeout，尚不能表达依赖跳过、等待决策、可恢复中断、检查点和跨脚本运行变量。
- 当前失败记录支持日志和截图路径，`proxy-adapter` 也有失败截图/DOM 样本基础，但尚无贯通版本、场景、脚本调用和步骤的统一证据包。
- 当前 `proxy-adapter` 已有 MCP 浏览器工具、实时 MJPEG 画面、DOM marker、高亮事件、动作执行器和交互日志，但尚无面向 E2E 语义脚本的正式执行与事件契约。
- 当前 `ai-chat-service` 已有 Agent 工具循环、MCP client/ToolRegistry 和 `vision.find_element`；通用单次页面状态分析与 Skills runtime 尚未实现。
- 当前 `ai-e2e` 主要使用纯文本生成接口，尚未实现主代理/页面子代理的任务图、上下文隔离、暂停决策和恢复运行时。
- 当前 `ai-e2e` UI 尚未集成测试浏览器的实时画面、语义步骤时间线和统一证据浏览。

## 10. 尚待技术设计的内容

以下内容没有在需求探查中锁定，不得直接当作已确认方案：

- 数据表、API、SSE/MCP 事件和跨服务关联字段的精确结构。
- 语义脚本 DSL 的字段、动作集合、断言集合和条件/循环表达方式。
- 浏览器会话、BrowserContext、账号和并发执行的隔离策略。
- 主代理与子代理运行时的具体会话复用条件和恢复时限。
- 决策文档的格式、审批层级和用户介入规则。
- 证据保留期限、存储介质、脱敏策略、trace/video 采集策略。
- 可视操作动画的表现、节奏和重放协议。
- 现有 TypeScript 脚本、历史项目和运行记录的迁移兼容方式。
- 标准 Playwright 文件导出能力。

## 11. 需求验收原则

后续技术方案至少需要证明：

1. 首次 PRD + 链接能够从零生成页面、模块、功能脚本和测试场景资产。
2. 后续运行能够加载同一业务版本，重新检查页面并复用或修复资产。
3. 复制业务版本后修改或修复脚本，不会改变来源版本。
4. 一个场景能够编排多个模块的多个功能脚本，并传递运行数据。
5. 子代理不能越权处理登录、造数或场景外任务；主代理能够根据上报进行恢复调度。
6. 主/子代理调用视觉模型时，每次都是独立、单次、完整输入的分析任务。
7. 所有浏览器操作通过 `proxy-adapter` 执行，并在实时画面与步骤记录中可观察。
8. 失败会保存截图与必要现场证据，并评估对后续依赖任务的阻碍。
9. 需要决策的任务能够暂停，决策写入版本文档后再恢复。
10. DOM 或定位变化只修复当前业务版本内受影响的功能脚本，并经过重新执行验证。
