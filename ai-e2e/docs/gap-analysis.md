# AI E2E 原始需求对照与缺口分析

> 本文用于回答一个非常具体的问题：**原始产品需求** 与 **当前 ai-e2e 实现** 之间，哪些已经对齐，哪些只是部分对齐，哪些仍然是明确技术缺口。
>
> 当口头需求、README、历史讨论与代码不一致时，以 **当前代码真实行为 + `requirements-baseline.md` + 本文结论** 为准。

## 1. 原始需求摘要

原始需求可以归纳为 4 个模式：

1. **PRD 分析模式**
   - AI 拆分 PRD
   - 先生成业务模块（L1）
   - 再生成功能模块（L2）
   - 生成功能对应测试内容
   - 文档生成后允许人工修改和补充

2. **探索模式**
   - 根据需求与站点页面进行探索
   - 将 URL 与功能模块绑定
   - 一个 URL 可绑定一个或多个功能模块
   - 一个功能模块必须至少有一个 URL
   - 绑定关系允许人工修改

3. **填充 / 生成模式**
   - 针对功能生成 Playwright 脚本

4. **执行模式**
   - 单纯执行 Playwright 脚本
   - 执行失败后 AI 介入
   - 输出问题分析结果，或者修正 Playwright 脚本

## 2. 总体判断

**结论：主方向没有偏航，核心工作流已经基本实现，但仍有 3 个明确技术缺口，以及 1 个需要锁定语义的实现偏差。**

当前 ai-e2e 已经具备：

- PRD / 需求分析
- 业务模块（L1）与功能模块（L2）生成
- 测试场景生成
- 页面探索
- URL 绑定建议与人工调整
- Playwright 脚本生成
- 脚本人工编辑与版本历史
- 脚本执行
- 单次运行失败诊断
- 可选自动修复

因此，当前问题不是“有没有做成这个产品”，而是：

- 哪些原始需求已经完整落地
- 哪些只做到了部分能力
- 哪些是下一步必须补齐的技术缺口

## 3. 按模式逐条对照

### 3.1 模式一：PRD 分析模式

**原始需求**

- AI 分析 PRD
- 拆成业务模块（L1）
- 再拆成功能模块（L2）
- 允许文档生成后人工修改与补充

**当前实现判断：部分对齐，核心链路已实现。**

#### 已实现

- 上传 PRD / 原始需求文本
- 生成业务模块（L1）
- 生成功能模块（L2）
- 生成测试场景
- 业务模块可编辑
- 功能模块可编辑

#### 未完全对齐

- 原始需求中的“允许人工修改和补充”，如果按严格含义理解，应该覆盖：
  - 模块
  - 场景
  - 脚本前的分析产物

当前代码只明确支持：

- 模块可编辑
- 脚本可编辑

但 **scenario（测试场景）本身没有完整独立编辑 API / UI 工作面**。

#### 结论

- **已实现核心目标**：需求拆分能力成立
- **存在技术缺口**：scenario 人工编辑不完整

---

### 3.2 模式二：探索与 URL 绑定模式

**原始需求**

- AI 探索站点
- URL 与需求 / 功能模块绑定
- 一个 URL 可绑定多个功能
- 一个功能一定有一个 URL
- 允许人工修改绑定关系

**当前实现判断：前半段对齐，后半段缺少强门禁。**

#### 已实现

- AI 驱动页面探索
- URL 绑定建议
- 绑定人工确认 / 调整
- 一个 URL 绑定多个功能模块的设计是成立的

#### 未完全对齐

- 当前状态机进入 `generating` 前，只检查 **项目中是否至少存在一个 URL binding**
- 当前并没有实现：
  - “每个功能模块都必须至少绑定一个 URL”的强校验
  - 未绑定功能模块清单
  - 阻断提示与修复入口

#### 结论

- **探索能力与绑定能力已实现**
- **“每个功能都必须有 URL”这一条没有被系统强制落地**

---

### 3.3 模式三：填充 / 脚本生成模式

**原始需求**

- 针对功能生成 Playwright 脚本

**当前实现判断：已实现，但实现颗粒度比原始表述更细。**

#### 已实现

- 生成 Playwright TypeScript 脚本
- 支持再生成
- 支持人工编辑脚本
- 支持版本历史

#### 语义偏差（需锁定，而不是立即视为 bug）

原始需求表述更像：

- **功能模块 → 脚本**

当前代码更接近：

- **测试场景 → 脚本**

这通常是合理的工程细化，因为一个功能模块下面往往会有多个测试场景。

#### 结论

- **脚本生成能力已实现**
- 需要在需求文档中明确“脚本生成单位”到底是：
  - 功能模块
  - 还是测试场景

如果不锁定，后续会持续产生口径漂移。

---

### 3.4 模式四：执行 + AI 介入模式

**原始需求**

- 执行 Playwright 脚本
- 失败后 AI 检查
- 输出问题报告或修正脚本

**当前实现判断：执行、单次诊断、可选修复已实现；项目级“问题报告”未实现。**

#### 已实现

- 执行单个脚本
- 执行项目下全部脚本
- 查看 run 历史
- 查看 run 详情
- 对单次失败做 AI 诊断
- 记录单次 run 的 intervention history
- 自动修复审批 / 拒绝流程

#### 未完全对齐

“输出问题报告”这句话有两种理解：

1. **单次失败诊断结果**
   - 当前已实现

2. **项目级失败汇总 / 根因分析报告 / 导出报告**
   - 当前未实现

#### 结论

- 如果把“问题报告”理解为 **run 级诊断结果**，当前已对齐
- 如果把“问题报告”理解为 **项目级汇总报告**，当前仍是明确缺口

## 4. 明确的技术缺口

> **状态更新（2025-05-15）**：以下 3 个技术缺口已全部实现完成。本文档保留作为历史对照参考。

下面 3 项不是建议，而是当前与原始需求相比最明确、最值得继续推进的缺口。

### Gap 1：每个功能模块必须绑定 URL 的强校验缺失 ✅ 已解决

**状态**：已于 2025-05-15 完成。

**实施细节**

- 状态机现在检查每个功能模块是否都有绑定
- 返回未绑定模块清单
- 前端显示未绑定模块提示（`UnboundModuleIndicator` 组件）

**原现状**

- 当前只保证"项目中至少有一个 URL binding"

**原问题**

- 不能阻止"部分功能模块未绑定 URL"却仍继续生成脚本

**原影响**

- 这是主流程正确性问题
- 会把未完成绑定的需求带进脚本生成阶段

**原优先级**

- **高**

---

### Gap 2：Scenario 编辑能力不完整 ✅ 已解决

**状态**：已于 2025-05-15 完成。

**实施细节**

- 提供 `TestScenarioService`（get/update/list）能力
- 路由 GET/PUT `/api/projects/:id/scenarios`
- UI：`ScenarioPanel` + `ScenarioEditor` 组件

**原现状**

- 模块可编辑
- 脚本可编辑
- 场景缺少完整独立编辑工作面

**原问题**

- 原始需求中的"文档生成后允许人为修改和补充"没有完整落到测试场景层

**原影响**

- 人工无法完整修订 AI 生成的分析产物

**原优先级**

- **高**

---

### Gap 3：项目级诊断报告未实现 ✅ 已解决

**状态**：已于 2025-05-15 完成。

**实施细节**

- API：`/api/projects/:id/diagnosis/report`
- 支持项目级失败聚合、根因分类统计
- 导出能力：JSON / HTML
- UI：`ReportPanel` + 可视化图表
- 数据库迁移 013 添加 `FailureType` 枚举

**原现状**

- 当前诊断是 run 级别
- 可以查看单次 run 的 intervention history

**原问题**

- 缺少项目范围的失败汇总、根因分类、导出报告

**原影响**

- 会影响批量执行后的治理、复盘和汇报能力

**原优先级**

- **中**

## 5. 需要锁定的语义点（否则后续继续漂）

### 5.1 “一个功能一个脚本”还是“一个场景一个脚本”

当前实现更接近 **一个测试场景生成一个脚本**。

如果产品层最终希望：

- 一个功能模块下只维护一个聚合脚本

那么需要单独调整脚本生成与存储模型。

如果接受当前实现，则必须在需求文档中写死：

- **当前脚本生成单位为测试场景，不是功能模块本身。**

### 5.2 “问题报告”是 run 级还是 project 级

当前代码支持的是：

- run 级诊断结果

尚不支持：

- project 级失败汇总报告

因此，任何需求文档都不应该把这两者混写。

- PRD → 模块拆分
- 探索 + URL 绑定建议
- 脚本生成
- 脚本执行
- 单次失败 AI 诊断
- 可选自动修复

### 部分对齐（已全部解决 ✅）

- 人工修改补充：模块 / 绑定 / 脚本 / scenario 均完整支持 ✅
- 问题报告：run 级 + project 级均支持 ✅
- URL 绑定规则：已强制要求每个功能模块绑定 URL ✅

### 明确技术缺失（已全部实现 ✅）

1. **每功能模块 URL 强绑定校验** ✅ 已实现
2. **Scenario 编辑能力** ✅ 已实现
3. **项目级诊断报告** ✅ 已实现
