# AI E2E 原始需求对照与缺口分析

> 状态：`deprecated` 历史对照。本文记录 2026-06-05 阶段的旧需求与实现差距，不再作为当前目标或缺口权威来源。
>
> 当前已确认目标以 `requirements-baseline.md` 为准，当前实现与 requirement gap 以代码和 `../PRODUCT-SPEC.md` 为准。本文不得用于直接制定新的开发目标。

## 1. 原始需求摘要

原始需求可以归纳为 4 个模式：

1. **PRD 分析模式**
   - AI 拆分 PRD
   - 先生成业务模块（L1）
   - 再生成功能模块（L2）
   - 生成功能对应测试内容
   - 文档生成后允许人工修改和补充

2. **探索模式**
   - 根据需求与站点页面进行探索
   - 将 URL 与功能模块绑定
   - 一个 URL 可绑定一个或多个功能模块
   - 一个功能模块必须至少有一个 URL
   - 绑定关系允许人工修改

3. **填充 / 生成模式**
   - 针对功能生成 Playwright 脚本

4. **执行模式**
   - 单纯执行 Playwright 脚本
   - 执行失败后 AI 介入
   - 输出问题分析结果，或者修正 Playwright 脚本

## 2. 总体判断

**结论：主方向没有偏航，核心工作流已经基本实现。第一批 3 个技术缺口已全部解决，第二批 3 个技术缺口在 2026-06-05 首次完整 E2E 验收后识别。**

- 脚本执行

- 可选自动修复
- 项目级诊断报告

### 3.5 模式五：脚本质量链路 — 部分对齐（2026-06-05 新增）

> 首次完整 E2E 验收暴露了一个之前未被识别的端到端质量问题：脚本质量不是孤立的，而是由一条完整的数据链路决定。

**隐含需求**

- 生成的脚本能正确执行
- AI 选择的选择器与目标应用实际 DOM 匹配

**当前实现判断：链路已通，但质量受前置数据制约。**

#### 已实现

- 脚本生成的完整数据管道：PRD → 模块 → 场景 → 快照 → 脚本
- 脚本执行引擎（`npx tsx` + Playwright Library API）
- 失败诊断与自动修复

#### 未完全对齐

脚本质量受以下因素串联影响：

1. **探索阶段是否获取到 DOM 快照**（`page_snapshot_json`）
2. **快照数据是否传递到脚本生成模板**（`{{page_snapshot}}`）
3. **AI 是否遵守模板中的 API 约束**（不使用 test()/expect()/waitForLoadState）
4. **AI 是否选择正确的选择器**（基于快照而非编造）

当 1-4 全部满足时，脚本质量可接受；任一环节断裂，通过率急剧下降。

#### 验收数据

| 指标         | 数值                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------ |
| 目标应用     | debug-ui（HashRouter SPA，2 个路由）                                                       |
| 测试脚本数   | 280                                                                                        |
| 通过数       | 13 (4.6%)                                                                                  |
| 失败数       | 268 (95.4%)                                                                                |
| 主要失败类型 | typescript 前缀(75), 选择器超时(54), 断言不匹配(33), strict_mode(33), waitForLoadState(26) |

**结论**：完整链路已打通，但脚本质量严重依赖快照数据完整性和 AI 模板约束执行力。

## 4. 明确的技术缺口

### 第一批（已全部实现 ✅）

1. **每功能模块 URL 强绑定校验** ✅ 已实现（2025-05-15）
2. **Scenario 编辑能力** ✅ 已实现（2025-05-15）
3. **项目级诊断报告** ✅ 已实现（2025-05-15）

### 第二批（2026-06-05 验收后识别）

#### Gap 4：SPA 探索能力缺失 ✅ 已实现

**原问题**：BFS 爬取策略对 HashRouter/History API SPA 发现 0 个 URL。探索阶段对 SPA 应用完全无效。

**当前实现**：`ExplorerService` 保留既有 BFS/AI 链路，同时通过显式装配的 `AiE2eRuntimeClient.executeScript()` 安装 History API / `hashchange` 观察器，读取渲染后 DOM 链接与常见 router 属性，并扫描可访问的 router 配置对象来补充 SPA 路由。

**影响**：SPA URL 不再只能手动添加，探索阶段可为 URL 绑定与快照链路提供更多自动发现入口。

**优先级** — **高**

#### Gap 5：page_snapshot_json 缺失降级

**问题**：手动添加的 URL 不经过探索流程，`page_snapshot_json` 为 NULL。脚本生成模板 `{{page_snapshot}}` 为空时，AI 编造选择器。

**影响**：快照缺失时脚本通过率 4.6%。这是脚本质量的**关键前置条件**。

**数据链路**：`探索 → getSnapshot() → urls.page_snapshot_json → {{page_snapshot}} → AI 选择器 → 脚本通过率`

**优先级** — **高**

#### Gap 6：脚本生成后验证缺失

**问题**：AI 偶尔违反模板约束（生成 test()/expect()、typescript 前缀、waitForLoadState），无自动检测和修正。

**影响**：280 脚本中 75 个含 typescript 前缀、26 个含 waitForLoadState，全部执行失败。

**优先级** — **中**

## 5. 需要锁定的语义点

### 5.1 "一个功能一个脚本"还是"一个场景一个脚本"

**已锁定**：当前脚本生成单位为**测试场景**，不是功能模块本身。

### 5.2 "问题报告"是 run 级还是 project 级 ✅ 已对齐

当前代码已支持：

- run 级诊断结果 ✅
- project 级失败汇总报告 ✅

### 5.3 "探索阶段"对 SPA 的有效性（2026-06-05 新增）

当前探索器对传统多页应用继续使用 BFS/AI 链路；对 SPA 应用（HashRouter / History API）会额外读取渲染后 DOM、History API / `hashchange` 观察结果和可访问 router 配置。任何关于"AI 驱动页面探索"的文档，应注明它是 SPA-aware 的 best-effort 探索，而不是仅靠静态 HTML 链接。

### 5.4 "脚本质量"的决定因素（2026-06-05 新增）

脚本质量取决于：`page_snapshot_json → {{page_snapshot}} → AI 选择器 → 通过率`。任何关于脚本质量的讨论，必须先确认快照数据是否完整。
